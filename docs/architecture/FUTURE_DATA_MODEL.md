# Ryvix Future Data Model & Phased Schema Roadmap

## 1. Executive Summary

To prevent premature schema inflation, Ryvix maintains a strict boundary between:
1. **CURRENT PHASE REQUIRED (Phase 1 Baseline)**: The core foundational tables needed for multi-tenant organizations, profiles, projects, multi-channel tasks, AI plans, and an immutable audit ledger.
2. **FUTURE PHASE REQUIRED (Phases 3–10)**: Entities scheduled for subsequent feature rollouts (connectors, telemetry time-series, security incidents, recovery runs, and workspace sandboxes).

---

## 2. Current Phase Required (Phase 1 Baseline)

These 6 tables are defined and fully validated in [`supabase/migrations/20260921000001_phase1_core_schema.sql`](../../supabase/migrations/20260921000001_phase1_core_schema.sql):

| Table Name | Primary Purpose | Security / Invariants |
| :--- | :--- | :--- |
| **`organizations`** | Multi-tenant customer accounts. | RLS tenant isolation; unique slug. |
| **`profiles`** | User records linked to `auth.users(id)`. | Automatic provisioning via `on_auth_user_created` trigger. |
| **`projects`** | Customer repositories & environments. | Scoped to parent organization. |
| **`tasks`** | Units of work from Web, WhatsApp, or Gmail. | Tracked from `queued` to `completed` / `failed`. |
| **`plans`** | Multi-step plans generated by AI. | Step-level `requires_approval` gates. |
| **`audit_events`** | Tamper-evident ledger. | `REVOKE UPDATE, DELETE` enforced. |

---

## 3. Future Phase Required (Documented & Scheduled)

These tables are **NOT** included in Phase 1 to prevent bloat. They are architecturally planned for subsequent phases:

### Phase 3: Repository & Version Control
- **`repositories`**: GitHub repository ID, full name, default branch, clone URL.
- **`repository_connections`**: GitHub App installation IDs and webhook secrets.
- **`pull_requests`**: Created branch name, PR number, unified diff references, merge status.

### Phase 4: AI Model Tracking & Token Accounting
- **`model_providers`**: Registered LLM providers (Hugging Face, OpenAI, Anthropic, vLLM).
- **`model_runs`**: Token counts (prompt/completion), latency, cost, and raw prompt hashes.
- **`tool_calls`**: Tool requested, input parameters hash, authorization status, and execution duration.

### Phase 5: Coding Workspace Sandboxes
- **`workspace_profiles`**: Pre-configured runtime images (Node, Python, .NET, Rust, Go).
- **`workspace_sessions`**: Container ID, allocated cgroups (CPU/RAM), port forward mappings, expiration time.
- **`code_diffs`**: AST diff hunks applied during coding tasks.
- **`previews`**: Ephemeral preview subdomains, active container ports, and TTL expiry.

### Phase 6-7: Connectors & Infrastructure Telemetry
- **`connectors`**: Connector type (`server_inband`, `server_cloud`, `whatsapp`, `gmail`, `github`).
- **`connector_credentials`**: Encrypted KMS tokens and SSH key fingerprints.
- **`connector_capabilities`**: Whitelisted actions permitted per connector.
- **`connector_events`**: Connection heartbeat transitions, enrollments, and status updates.
- **`telemetry_metrics`**: Rollup tables for CPU, RAM, Disk, IOPS, and network throughput.
- **`telemetry_logs`**: Compressed, partitioned log chunks from `/var/log/syslog` and `/var/log/auth.log`.
- **`health_checks`**: Periodic HTTP/TCP availability check records.

### Phase 8: Security & Autonomous Self-Healing
- **`security_events`**: Detected threat events (SSH brute force, privilege escalation, cryptominers).
- **`incidents`**: Aggregated anomaly incidents with AI forensic diagnosis.
- **`recovery_actions`**: Pre-approved remediation recipes (`service.restart`, `log.truncate`, `firewall.block_ip`).
- **`recovery_runs`**: Execution status, attempt counter (1-3), post-action verification results, and cooldown timestamps.

### Phase 9-10: Multi-Channel Communication & Deployments
- **`notifications`**: Dispatch queue and delivery statuses for WhatsApp messages and Gmail digests.
- **`deployments`**: Production deployment webhooks, rollback triggers, and verification health checks.

## 4. Architectural Separation Boundary

```
[ PHASE 1 BASELINE (MIGRATION ACTIVE) ]
organizations ──► profiles (auth.users)
      │
      └──► projects ──► tasks ──► plans
              │
              └──► audit_events (IMMUTABLE)

══════════════════════════════════════════════════════════════════
[ FUTURE PHASES (SEPARATED ARCHITECTURALLY) ]
Phase 3:  repositories, pull_requests
Phase 4:  model_runs, tool_calls
Phase 5:  workspace_sessions, workspace_profiles, previews
Phase 6:  connectors, connector_credentials, connector_capabilities
Phase 7:  telemetry_metrics, telemetry_logs, health_checks
Phase 8:  security_events, incidents, recovery_actions, recovery_runs
Phase 9:  notifications (WhatsApp / Gmail)
Phase 10: deployments
```
