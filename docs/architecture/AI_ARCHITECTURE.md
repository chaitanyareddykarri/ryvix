# Ryvix AI Architecture Specification

## 1. Role and Boundary of the Intelligence Layer

In Ryvix, the AI Model acts strictly as an **intelligence and reasoning engine**. It processes user intentions, analyzes technical contexts, formulates structured execution plans, generates code modifications, and conducts incident investigations.

```
                      +----------------------------------+
                      |         Hugging Face AI          |
                      |   Dedicated Inference Endpoint   |
                      |   - Planning & Reasoning         |
                      |   - Code Generation / Diffs      |
                      |   - Tool Selection               |
                      |   - Incident Root-Cause Analysis |
                      +----------------------------------+
                                       ^
                                       | Structured Prompts & Tools
                                       | Structured JSON Responses
                                       v
                      +----------------------------------+
                      |     Ryvix AI Gateway Service     |
                      |   - Context Builder & Pruner     |
                      |   - Tool Registry Validator      |
                      |   - Response Parser & Formatter  |
                      +----------------------------------+
                                       ^
                                       |
                                       v
                      +----------------------------------+
                      |     Ryvix Backend Orchestrator   |
                      +----------------------------------+
```

### What the AI Model IS:
- A reasoning engine capable of understanding code structures, runtime traces, and system logs.
- A planning engine that creates phased execution steps for tasks.
- A code modification generator that outputs precise unified diffs or targeted file replacements.
- A forensic investigator that identifies root causes from telemetry and anomaly reports.

### What the AI Model is NOT:
- **NOT** the database or storage layer.
- **NOT** the authentication or authorization system.
- **NOT** the holder of GitHub tokens, cloud API keys, or server credentials.
- **NOT** an unrestricted shell executor on customer infrastructure.

---

## 2. Model Hosting & Hugging Face Deployment

Ryvix decouples the AI intelligence layer from the application backend by hosting the model independently on **Hugging Face**:
- **Inference Mode**: Dedicated Hugging Face Inference Endpoints or serverless Inference APIs with low-latency container runtimes.
- **Protocol**: Standardized OpenAI-compatible chat completion endpoints or native Hugging Face text-generation inference (TGI) with streaming tokens.
- **Hardware Isolation**: GPU-accelerated infrastructure running in isolated VPCs, communicating with the Ryvix backend over authenticated TLS channels.

---

## 3. Context Compilation & Token Management

Before dispatching an inference request to the model, the `Ryvix AI Gateway` compiles a concise, high-signal context package:

1. **System Prompt**: Defines the persona, engineering rules, security constraints, and tool invocation conventions.
2. **Project Context**: Generated by the Project Analyzer:
   - Programming languages, frameworks, package managers, and runtime versions.
   - High-level directory tree and key configuration files (e.g. `package.json`, `Dockerfile`, `docker-compose.yml`).
3. **Task Context**: The user's prompt, active branch/commit, conversation history, and user preferences.
4. **Diagnostic Telemetry (if incident-related)**: Sanitized logs, metric spikes, recent deployment events, and anomaly signatures (pruned to fit within token budgets).
5. **Tool Catalog**: JSON schemas of available tools (e.g., `read_file`, `plan_step`, `generate_diff`, `run_workspace_tests`, `query_logs`).

---

## 4. Structured Tool Calling & Validation

The AI communicates its decisions exclusively via structured tool calls. The backend validates all calls against strict Pydantic / Zod schemas before execution.

### Tool Call Lifecycle:
1. **Model Generation**: The model selects a tool (e.g., `modify_file`) with arguments.
2. **Backend Interception**: The Ryvix Backend validates arguments against schemas and checks user permissions.
3. **Policy Evaluation**: If the tool is destructive, execution pauses for customer approval.
4. **Execution**: A dedicated worker executes the tool in an isolated sandbox or connector bridge.
5. **Tool Output Return**: Execution stdout/stderr/results are fed back into the AI's conversation history for the next reasoning step.

---

## 5. Model Evolution & Fine-Tuning Strategy

Ryvix avoids training foundation models from scratch. Instead, it follows a multi-stage adaptation lifecycle:

```
[ Capable Foundation Model ] (e.g., Llama 3 / Mistral / DeepSeek)
             │
             ▼
[ Prompt Engineering & Tool Scaffolding ]
  - Precise domain-specific system prompts
  - Project and runtime context injection
  - Verified tool-calling protocols
             │
             ▼
[ Production Execution & Telemetry Collection ]
  - Collecting verified user requests, successful plans, correct diffs, and recovery steps
             │
             ▼
[ Data Sanitation & Quality Filtering ]
  - Strip all PII, secrets, credentials, and customer IP
  - Discard failed runs, hallucinations, or rejected plans
             │
             ▼
[ Fine-Tuning & Specialized LoRA Adapters ]
  - Fine-tune custom Ryvix models for repo analysis, incident triage, and stack-aware coding
             │
             ▼
[ Deployment on Hugging Face ]
```

### Dataset Sanitization Rules:
- **No Secrets**: Automatic regex and entropy scanning filters out tokens, keys, and passwords.
- **Anonymization**: Customer repository names, domains, and internal IPs are replaced with generic tokens.
- **Success Verification Only**: Only modifications verified by automated tests, successful builds, and explicit customer approvals enter the fine-tuning corpus.
